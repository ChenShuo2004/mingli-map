# 最小知识模型

## 目的

这份模型只回答一个问题：不同来源中的知识，进入项目后最少需要保留哪些结构，才能被探索、比较和追溯。

它不是最终数据库设计。只有真实仓库或用户使用暴露出问题时，才增加字段或拆分实体。

## 九类核心记录

### 1. 专题 `topic`

一门可以独立进入的知识体系，如八字、六爻或塔罗。

最小字段：

- `id`：稳定、唯一的内部标识；
- `name`：主要名称；
- `aliases`：别名；
- `summary`：中性简介；
- `status`：草稿、待核验或已核验；
- `source_refs`：支撑简介和边界的来源。

### 2. 知识节点 `concept`

专题内部可以单独解释和连接的概念。一个节点不等于一篇完整文章。

最小字段：

- `id`、`name`、`aliases`；
- `topic_ids`：出现在哪些专题；
- `summary`：当前中性解释；
- `prerequisite_ids`：理解前需要知道什么；
- `source_refs`；
- `status`。

### 3. 规则 `rule`

来源中明确表达的计算、判断、转换或解释规则。规则必须与概念解释分开。

最小字段：

- `id`、`name`；
- `inputs`、`conditions`、`outputs`；
- `scope`：适用专题、流派或场景；
- `source_refs`；
- `implementation_refs`：规则在外部仓库中的文件和代码位置；
- `status`。

代码实现只能证明“该项目采用了这条规则”，不能单独证明规则正确。

### 4. 关系 `relation`

连接两个记录，不把所有连接都压成父子目录。

第一批允许的关系：

- `broader` / `narrower`：上下位；
- `requires`：前置知识；
- `part_of`：组成部分；
- `related_to`：直接相关；
- `derived_from`：历史或概念来源；
- `contrasts_with`：存在明确差异；
- `used_by`：某概念或规则被某方法使用。

每条关系应记录 `source_refs` 或项目判断依据。

### 5. 说法 `claim`

某个来源对概念、规则或历史作出的具体陈述。它用于保留分歧，而不是急于生成唯一答案。

最小字段：

- `id`；
- `subject_id`：陈述对象；
- `statement`：尽量短的转述；
- `source_refs`；
- `viewpoint`：作者、项目或流派；
- `status`：来源陈述、待交叉核验、已交叉核验或有争议。

### 6. 解释 `explanation`

来源或体系如何把规则结果解释成人可理解的含义，包括体感、事象、生活领域、叙述模板和固定案例中的解释。它不等于规则，也不等于事实。

最小字段：

- `id`、`subject_ids`；
- `text` 或结构化解释要点；
- `domain`：健康、婚姻、财富、性格、职业等；
- `viewpoint`：项目、作者或流派；
- `source_refs`；
- `publication_boundary`：内部来源层、可公开候选或排除；
- `status`。

个人领域断语可以进入受限来源层，但不能因此变成面向用户的个人测算功能。

### 7. 方法与案例 `method`

用于组织、检验或帮助理解知识的工作流、评分方法、反倒推纪律、推理回放、固定案例和跨体系映射。

最小字段：

- `id`、`name`、`method_type`；
- `steps`、`inputs`、`outputs` 或 `mapping`；
- `learning_purpose`；
- `source_refs`；
- `status`。

固定案例的项目预期只证明实现行为，不能当作独立知识证据。风水、塔罗等跨体系映射必须同时连接两个专题，并标明是作者设计、传统说法还是已核验关系。

### 8. 来源 `source`

知识追溯的入口，包括 GitHub 仓库、文件、古籍、论文、课程和网页。

最小字段：

- `id`、`title`、`source_type`；
- `creator`；
- `url` 或本地定位；
- `accessed_at`；
- `license`、`license_scope`；
- `location`：文件、章节、行号、时间戳或提交版本；
- `reliability_notes`；
- `status`。

### 9. 视觉资产 `visual_asset`

承载知识结构、推演结果或辅助理解的图像。视觉资产不是普通附件，必须能连接到知识节点和来源。

第一批资产类型：

- `explanatory_diagram`：概念、关系、步骤或结构图解；
- `chart_example`：命盘、星盘、卦盘等生成结果样例；
- `table_or_reference`：图形化对照表和速查表；
- `source_screenshot`：用于核验的界面或原始资料截图；
- `illustration`：帮助理解但不直接表达规则的插图。

最小字段：

- `id`、`title`、`asset_type`；
- `source_refs`：来自哪个仓库、文件或网页；
- `original_location`：原始路径或下载地址；
- `local_path`：项目内归档位置；
- `linked_record_ids`：关联的专题、概念、规则或说法；
- `caption`、`alt_text`：说明图中表达什么；
- `creator`、`license`、`license_scope`；
- `checksum`：识别原文件并避免重复；
- `generation`：如果是生成图，记录工具、版本、输入参数和复现方式；
- `publication_status`：仅内部核验、可公开原图、需重绘、需重新生成或排除；
- `status`。

同一张图可以同时保存三个层次，但不得互相覆盖：

```text
原始文件：保留来源证据
→ 处理版本：裁切、标注或格式转换
→ 对外版本：获得授权的原图、可复现生成图或自行重绘图
```

命盘等生成结果优先记录生成参数并尝试重新生成。只有图片而没有输入和规则时，只能作为来源样例，不能据此反推确定规则。

## 内容进入流程

```text
外部仓库
→ 来源记录
→ 找到知识所在文件、代码或图片位置
→ 拆成概念 / 规则 / 说法 / 解释 / 方法与案例 / 视觉资产
→ 建立必要关系
→ 对照第二来源
→ 决定是否进入对外知识地图
```

## 辅助理解的交互

知识地图可以使用交互呈现知识，但每个交互都必须连接到明确的学习目的和知识记录。第一阶段允许的类型包括：

- 展开或折叠概念层级；
- 高亮节点之间的关系；
- 回放一个固定案例的结构生成步骤；
- 在固定命盘、星盘或卦盘上显示术语解释；
- 比较不同体系、流派或来源的异同；
- 按来源、媒介、用途等标签筛选知识；
- 搜索术语并跳转到相关节点。

以下情况视为实操功能，不属于当前范围：要求用户输入出生信息、问题、抽取结果或其他个人数据，并生成面向该用户的命盘解释、吉凶判断或行动建议。

对外部仓库中的辅助理解工具，先在仓库盘点中记录其学习目的、依赖的数据、许可和可拆分程度，再决定复用、改造还是自行实现。暂不为交互单独建立正式数据实体。

## 边界原则

- “专题”解决从哪里进入，“标签”描述它有什么属性，两者不要混用。
- “概念”解释事物，“规则”表达如何计算或判断，两者不要混用。
- “来源说了什么”与“项目最终如何表述”分开保存。
- “程序如何判断”与“作者如何解释结果”分开保存。
- 当前页面没有对应专题，不是丢弃来源知识的理由；先按真实领域分类，再决定何时公开。
- 多个来源文字相似不等于独立验证，可能来自同一上游资料。
- 图片必须连接到它帮助解释的记录；无法说明用途的装饰图片不进入知识资产。
- 暂时无法归类的内容进入盘点记录，不为容纳一个样本立刻扩充正式模型。
