# GitHub 知识仓库收录章程

## 目的

这份章程用于连续处理大量包含命理、占卜或人格测验知识的 GitHub 仓库。目标不是把每个仓库整体搬进项目，而是稳定完成：

```text
锁定来源 → 全量盘点 → 逐项处置 → 单库验收
→ 跨库比较 → 保留一致与分歧 → 核验来源 → 晋级正式知识
```

硬门槛：一个仓库没有完成单库验收前，不启动它与其他仓库的正式比较。单库验收同时要求“文件级覆盖”和“知识级覆盖”；只有逐文件台账、没有把知识内容拆出分类，不能算完成。已有的提前比较可以保留，但必须标为 `provisional`，待单库完成后重跑。

## 一、四层存储

### 1. 仓库盘点层

位置：`intake/repositories/`

每个仓库一份 Markdown 记录，回答：

- 知识在哪些文件、表格、代码或图像中；
- 仓库和上游资料的许可如何；
- 哪些是原始材料、作者转述、程序规则或个人结论；
- 哪些值得提取，哪些只作索引，哪些排除；
- 与已有来源有哪些一致、差异和可能的共同上游。

盘点文件是人可读的调查结论，不是正式知识数据。

### 2. 来源层

位置：`data/sources/{source_id}/`

忠实保存锁定 commit 中所有进入项目范围的提取结果。必须：

- 保留仓库 URL、commit、原文件路径和校验值；
- 尽量使用脚本从锁定版本重新生成；
- 保留对方的值和分类，不在提取时“修正”它；
- 对未核验数据标记 `single_source` 和 `internal_review_only`；
- 有争议时保留各方原数据，不相互覆盖。

来源层的“已保存”不等于“已认可”。

每条知识至少分开记录四个维度，不能再互相代替：

- `knowledge_status`：是否已提取为可理解的知识；
- `consensus_status`：共识、流派说法、作者实现、冲突版本或待核验；
- `rights_status`：原文、代码或素材能否复制和公开；
- `use_boundary`：能否用于公开解释、研究比较或个人判断。

版权不明只限制原文复制和公开复用，不自动阻止阅读、分类、提取结构和撰写原创摘要；非共识只是一种知识状态，不是排除理由。

### 3. 来源比较层

位置：`data/comparisons/`

当两个以上来源描述同一概念、表格或规则时，建立比较记录，至少包含：

- `subject`：比较对象；
- `source_refs`：参与比较的来源；
- `agreement`：完全一致的项；
- `differences`：值、顺序、缺失、范围或解释差异；
- `upstream_relationship`：是否可能相互复制或共用上游；
- `verification_targets`：需查找的书、版本、章节、网页或论文；
- `status`：`implementation_match` / `disputed` / `cross_checked`。

实现一致不自动等于 `cross_checked`。只有确认来源相互独立并能定位支持内容时，才能升级。

进入这一层前，参与比较的每个 GitHub 仓库都必须已经达到 `repository_complete`。

### 4. 正式知识层

位置：`data/knowledge/`

这一层只保存我们自己的结构化知识记录：`topic`、`concept`、`rule`、`relation`、`claim`、`source` 和 `visual_asset`。

正式知识使用自己的中性转述，通过 `source_refs` 连回来源层，不复制大段仓库文案。

## 二、新仓库的八步流程

所有进入知识级处理的内容，都必须在 `docs/KNOWLEDGE_OUTLINE.md` 中找到最细的对应节点。大纲是跨仓库的归档入口；来源正文仍保存在来源层，不直接堆进大纲。模块与节点的机器可读连接统一生成到 `data/knowledge-outline-index.json`，不回写或污染锁定 commit 的来源提取文件。

### 第 1 步：登记与锁定

- 记录仓库 URL、所有者、默认分支、commit 和检查日期。
- 使用 commit 而不是浮动的 `main` 作为提取基准。
- 检查 LICENSE、README、依赖和上游声明。

未锁定 commit 的仓库不进入提取。

### 第 2 步：资产盘点

分开检查：文档与结构化数据、映射与规则代码、长文与个人结论、视觉资产、纯粹帮助理解的交互工具。此步只定位，不批量复制。

### 第 3 步：内容分级

| 类别 | 说明 | 处理 |
|---|---|---|
| A 基础映射 | 固定对照与结构化基础表 | 优先提取最小数据集 |
| B 推演规则 | 条件、输入、输出和适用范围 | 提取规则索引，再逐条追源 |
| C 来源说法 | 作者、流派或书籍的具体陈述 | 作为 `claim` 候选 |
| D 项目参数 | 权重、分数、阈值、算法顺序 | 只记为“该项目采用” |
| E 长文或语料 | 古籍全文、课程、解读文案 | 全文阅读后提取主题、结构、说法与原创摘要；权利和底本不清时不复制正文，但不能停在文件名索引 |
| F 个人结论 | 健康、婚姻、财运、行动建议等 | 作为来源解释完整分类保存，标记为个人领域断语；不直接公开、不当作共识、不提供个人测算 |
| G 理解工具 | 固定案例、比较、回放、术语提示 | 单独检查学习目的和许可 |

### 第 4 步：样本验证

首次遇到新的文件形态或知识结构时，先用少量样本验证提取方法：

- 1–4 组结构化基础数据；
- 1 组规则索引；
- 1 组分歧或特色说法；
- 1 组视觉或交互样本。

样本验证只是防止错误批量处理，不代表仓库收录完成。验证通过后必须回到同一仓库继续完成全部相关资产。

### 第 5 步：单库全量处理

同时建立“资产处置清单”和“知识模块清单”。每个相关目录、文件组、数据表、规则模块、文档组、视觉资产和理解工具都必须落到以下一种结果；每个有知识内容的模块还必须拆出它包含的概念、规则、关系、解释、流派说法、项目参数或跨体系映射：

| 结果 | 含义 |
|---|---|
| `extracted` | 已忠实提取到来源层，并可追溯或复现 |
| `summarized` | 已阅读完整内容并提取主题、结构、来源说法和原创摘要；原文因权利边界不复制 |
| `indexed` | 不复制正文或资产，但已保存范围、数量、位置、校验值和原因 |
| `excluded` | 明确超出项目边界、无知识价值或权利不允许，并记录原因 |

`看到但未处理`、`以后再说`、`只抽了几个代表文件`、`只保存文件名和函数名但没有保存知识内容`都不能算完成。发现待核验内容时仍按来源原貌提取，并标记 `single_source`；待核验不是跳过处理的理由。超出当前公开产品边界的个人断语、其他术数或跨体系映射也进入来源层，只是单独分类和限制发布。

### 第 6 步：单库验收

只有同时满足以下条件，仓库状态才能改为 `repository_complete`：

- 完整资产清单已经覆盖相关目录与文件组；
- 完整知识模块清单已经覆盖仓库内所有领域，而不是只覆盖当前正在制作的专题；
- 清单中没有 `unreviewed`、`pending` 或无去向项目；
- 所有范围内资产均已 `extracted`、`indexed` 或 `excluded`；
- 所有有知识内容的模块均已把实际知识、来源说法或原创摘要提取到来源层；内容权利问题只能阻止复制正文，不能用文件索引代替知识提取；只有无法安全读取的隐私材料、二进制资产或确无知识内容的文件可以只建索引；
- 来源元数据、原路径、commit、许可和校验信息完整；
- 提取脚本、索引统计和定向测试可重跑；
- 盘点文档已经写明单库产生的新知识候选、项目规则、个人解释、其他体系知识、风险与卡点。

### 第 7 步：去重、比较与外部核验

开始比较前，为每个知识项记录 `outline_id`。先在同一大纲节点内查找已有概念、规则、关系、说法、解释和案例，再判断它是重复来源、补充证据、差异版本、冲突说法或真正的新候选。找不到合适节点时先标记 `new_candidate`，只有真实材料证明现有节点无法容纳时才调整大纲。

新增仓库、知识目录、正式知识文件或大纲节点后运行：

```bash
python3 scripts/build-knowledge-outline-index.py
python3 scripts/build-knowledge-outline-index.py --check
```

检查必须同时满足：所有来源快照有默认路由、所有知识目录条目至少连接一个有效 `outline_id`、所有正式知识文件在大纲正文中有明确位置、生成索引与当前仓库状态一致。任何一项失败都不能结束本批收录。

| 结果 | 处理 |
|---|---|
| 文件校验值相同 | 记为副本，不增加独立证据数 |
| 数据完全相同，上游关系不明 | `implementation_match` |
| 数据相同，独立上游可确认 | 候选 `cross_checked` |
| 部分相同 | 分开记录一致项和差异项 |
| 相互冲突 | `disputed`，保留所有版本 |
| 一方是另一方转载或打包 | 建立上游关系，不当作独立来源 |

核验优先级：

1. 可定位的原始典籍、原作或一手文献；
2. 说明底本、版本和编辑过程的权威整理；
3. 经过校勘的图书、论文或专业数据库；
4. 其他独立实现，仅用于发现一致和差异；
5. 论坛、自媒体、问答和搜索摘要，只作线索。

使用浏览器搜索时，保留 URL、标题、作者、访问日期和指向的书籍或底本。搜索摘要不作最终证据。

### 第 8 步：晋级正式知识与批次收尾

满足以下条件才能进入 `data/knowledge/`：

- 有稳定内部 ID 和明确类型；
- 使用自己的中性转述；
- 保留至少一个可定位的 `source_ref`；
- 说明是共有映射、某流派说法、项目规则还是待验证假设；
- 权利和可公开范围已记录；
- 有分歧时使用多条 `claim` 并列，不生成虚假共识。

进入正式层不代表永久定稿。新资料可改变状态和适用范围，但不覆盖原来的来源记录。

每个仓库必须交付：

1. 一份仓库盘点文档；
2. 一条 `source.json`；
3. 一份覆盖全部相关资产的处置清单；
4. 全部范围内来源数据、索引或排除记录；
5. 运行或数据验证结果；
6. 单库验收结论；
7. 单库验收完成后生成的跨库比较结果；
8. 新决定、新分歧和新卡点。

此外，每个知识模块都必须连接至少一个 `outline_id`；每批收尾时更新相应大纲节点的来源、比较状态或候选项，并让 `scripts/build-knowledge-outline-index.py --check` 通过。没有实质性新知识、分歧或结构变化时，不为形式完整而修改大纲。

只有出现实质性新决定或新卡点时，才更新 `PROJECT.md`。

## 三、批量处理规则

### 批次大小

- 每批默认处理 3–5 个仓库。
- 同一批尽量属于同一专题，便于对照。
- 批次内逐个完成单库处理；全部达到 `repository_complete` 后再统一比较。
- 超过 5 个时先做列表和粗筛，不同时深度提取。

### 批次优先级

1. 有明确许可和结构化知识；
2. 能解释现有分歧；
3. 提供精确上游来源；
4. 有独特理解交互；
5. 只有大量个人解读或无许可的仓库最后处理。

### 停止条件

出现以下任一情况，首轮停在索引或盘点层：

- 无许可且内容主要为复制文本；
- 上游来源完全不明；
- 主要是个人测算与结论；
- 与已有来源为相同副本；
- 实际内容不足以改进知识模型。

## 四、一致、争议与错误

- **一致**：只说明实现结果一致，还需检查是否共用代码、课程、书籍或网络表格。
- **争议**：对象相同但值、顺序、定义或适用范围不同。保留各版本，寻找能解释差异的底本或流派资料。
- **错误**：只有无法从锁定 commit 重现、源文件内部矛盾、证明为解析/OCR/编码/实现错误，或虚构来源时才标记。标记后仍保留原值和判定理由。

## 五、完成标准

### 单个仓库完成

- 每个仓库都有锁定 commit 和盘点记录；
- 许可和主要上游依赖已记录；
- 全部相关资产均已提取、索引或排除，没有未处置项；
- 全部知识模块均有领域分类和实际内容去向；文件台账不能代替知识提取；
- 每一项都有原路径、处理理由和输出位置；
- 提取脚本、JSON/YAML、索引统计和定向测试通过；
- 状态为 `repository_complete`。

### 批次比较完成

- 参与比较的仓库都已通过单库验收；
- 已与现有数据比较，区分副本、实现一致和独立验证；
- 分歧数据全部保留；
- 已说明哪些可晋级、哪些待核验、哪些排除；
- `PROJECT.md` 只保留实质性新决定与卡点。
